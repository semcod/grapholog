Jak wybierany jest cel

Jawna reguła routingu ma pierwszeństwo. Bez niej wspólna funkcja znaleziona wewnątrz zarejestrowanej paczki wskazuje istniejący cel. Brak celu daje propozycję nowej paczki; kilku kandydatów daje ticket wyboru. Normalizacja AST nie dowodzi równoważności zachowania. Dlatego każdy wariant zaczyna się od projektu API i oceny zależności, efektów oraz licencji.

Planfile i GitHub

Propozycje przechodzą przez TicketProposalV1, a zapis przez create_ticket_deduplicated. Grapholog nie edytuje YAML ticketów ręcznie. Planfile pozostaje źródłem statusu, mapowań GitHub i potwierdzeń synchronizacji. Grapholog przechowuje plan, wiązania ticketów i dziennik prób delegacji.

Synchronizacja obejmuje wyłącznie tickety danego planu; odczyt korzysta z konkretnych przypisanych issues. Linki między repozytoriami trafiają do opisów. Częściowe powodzenie jest zachowywane, a ponowienie nie tworzy ponownie już przypisanych issues. Repozytoria wskazuje jawny katalog, sprawdzany względem konfiguracji Planfile i Git origin.

Koru i przekazanie artefaktów

koru ticket auto ID --project ROOT --queue grapholog --no-sync

Sprawdzono rzeczywiste polecenie Koru w trybie --dry-run: kod wyjścia 0, rozpoznany ticket, wykonawca llm i plik kontekstu. Uruchomienie produkcyjne wymaga własnej konfiguracji wykonawcy/modelu Koru. Pliki kontekstu zawierają zamknięty JSON Schema wyniku oraz GBNF; Grapholog nie ustawia sam constrained decoding w dostawcy Koru.

Każdy etap dostarcza grapholog.task-result.v1 związany z zadaniem i digestem wejścia. Weryfikacja paczki wymaga wersji, eksportów, testów z logami i dowodu przeglądu licencji. Manifest wyniku musi być dołączony do ticketu. Zweryfikowane pliki są kopiowane do lokalnego katalogu konsumenta przed przekazaniem zadania Koru.

Status done, zamknięcie issue lub exit code 0 nie wystarcza do migracji. Grapholog sprawdza sumy i strukturę dowodów oraz deklarowane wyniki; nie dowodzi, że raport modelu jest prawdziwy i nie uruchamia sam wszystkich testów. Anulowane zależności, needs_review, nieaktualny kod i brak artefaktu blokują dalszą pracę.

Co zostało przetestowane

  • 75 testów Pythona, w tym 20 scenariuszy ekstrakcji; 2 testy Rust.
  • 15 przypadków gramatyk w natywnym walidatorze llama.cpp, bez modelu.
  • Nowy i istniejący pakiet, niejednoznaczny katalog, scalanie grup oraz jeden ticket migracji na projekt.
  • Powtórzenia, odzyskanie mapowań, terminalne tickety, stare źródła, symlinki i zmienione artefakty.
  • Prawdziwy store i synchronizator Planfile; symulator granicy GitHub, w tym częściowa awaria oraz zamknięcie issue bez dowodów.
  • Delegacja do procesów testowych, kod 0 bez ukończenia oraz timeout. Prawdziwy Koru: parser i dry-run.
  • Zgodny plan przez CLI, MCP, REST i gRPC.

Nie wykonano wywołania LLM, automatycznego przeniesienia kodu użytkownika ani publikacji issues do jego konta GitHub. W paczce są implementacja, testy i odtwarzalny lokalny przykład; efekty zdalne i kod wykonuje skonfigurowany Koru po uruchomieniu komend wykonawczych.

Metodologia pomiaru

Planner 0.5 pracował na zapisanym syntetycznym indeksie 0.4: 200 projektów JS/TS, 4600 wybranych plików. Trzy przebiegi: 1.350, 1.179, 1.176 s. Pomiar obejmuje odczyt SQLite, wybór celów, DAG i walidację JSON Schema; nie obejmuje parsowania źródeł, zapisu Planfile, GitHub ani pracy LLM. Wybrano 20 rodzin źródłowych; funkcje testowe pozostały poza kandydatami. Plan ma 7,218,582 bajtów w zmierzonym kodowaniu JSON. To pomiar tego korpusu, nie limit ani gwarancja dla dowolnego workspace.

Użycie

grapholog tickets plan --db index.sqlite --config catalog.json -o plan.json
grapholog tickets materialize plan.json --db index.sqlite --state state.json
grapholog tickets sync --state state.json --execute
grapholog tickets run --state state.json --max-steps 20 --execute --sync-github
grapholog tickets catalog --state state.json -o next-catalog.json

Katalog zweryfikowanych paczek może zasilić następną analizę. Nowe paczki powstają we wskazanym projekcie; adapter nie tworzy zdalnych repozytoriów ani nie publikuje automatycznie do PyPI/npm. Katalog, routing i skonfigurowany wykonawca są częścią wdrożenia.
