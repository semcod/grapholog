Szybsze ponowne porównania projektów

Wdrożono trwały cache parsowania w Pythonie i Rust oraz ograniczoną liczbę workerów w Rust. Wszystkie zmierzone warianty zachowały wynik analizy wersji 0.2 po pominięciu nowego pola statystyk runtime.

5,01×Rust: 1500 plików na projekt; 0.2 → 0.3, ciepły cache + 4 workery
15,59×Rust: 60 plików na projekt; 0.2 → 0.3, ciepły cache + 4 workery
45 testów43 testy integracyjne/jednostkowe przez unittest i 2 natywne testy Rust

Przyspieszenia dotyczą dwóch korpusów syntetycznych, ponownego odczytu niezmienionych drzew i rozgrzanego cache systemu plików. Nie są gwarancją dla dowolnego repozytorium.

Co zmieniono

ObszarWdrożenie 0.3
Cache--cache-dir DIR w obu CLI. Zapis udanych wyników parsera, bez rozwiązań zależności. Ten sam plik może użyć wpisu również pod inną ścieżką lub w drugim projekcie.

RównoległośćRust: --jobs 1..64, własny parser i bufor każdego workera, wspólna kolejka plików. Sortowanie wyników przed rozwiązaniem zależności. Bez nowej zależności od Rayon.
OdpornośćJSON z sumą kontrolną, walidacja typu i nagłówka, atomowa zamiana pliku. Niedostępny lub uszkodzony wpis powoduje zwykłe parsowanie. Brak pickle i wykonywania analizowanego kodu.
Domyślne zachowanieCache wyłączony, Rust używa jednego workera. JSON zyskał dodatkowe pole runtime; statystyki nie zmieniają klasyfikacji różnic ani kodu wyjścia --check.

Pomiary pełnego CLI

Każda próba obejmuje diff A B --format json: inwentaryzację, odczyt i SHA-256 wszystkich zwykłych plików, parsowanie lub cache, powiązania, porównanie oraz pełną serializację JSON do /dev/null. Kompilacja, instalacja, tworzenie korpusu i sprzątanie cache pozostają poza pomiarem.

Metodyka i praktyczne ograniczenia

  • Jedna próba rozgrzewkowa i siedem mierzonych powtórzeń. Kolejność wariantów rotowana i odwracana. W tabelach mediana, zakres obserwowany i mediana szczytowego RSS procesu potomnego z wait4.
  • Cache systemu plików rozgrzany. Dla wariantów „pusty cache” nowy pusty katalog przy każdym pomiarze; dla „rozgrzany” wpisy z próby rozgrzewkowej.
  • Affinity: warianty szeregowe CPU 0; warianty 4-workerowe CPU 0–3. Limit kontenera: 8 CPU. Część zysku pochodzi z większej liczby dostępnych CPU, a nie wyłącznie z optymalizacji algorytmu.
  • AMD EPYC 9V74 80-Core Processor; Linux-6.18.44-x86_64-with-glibc2.39; Python 3.12.14; rustc 1.98.1.
  • Python: tree-sitter 0.25.2, tree-sitter-javascript 0.25.0, tree-sitter-typescript 0.23.2, tree-sitter-php 0.24.1, tree-sitter-bash 0.25.1. Natywne wersje gramatyk i parsera Rust zapisano w rust/Cargo.lock.
  • To małe syntetyczne projekty, zawierające JS/TS i dane; nie zmierzono tu dużych repozytoriów, zimnego dysku, NFS ani lokalnego Python AST. Różnica Python 0.2 → 0.3 bez cache nie jest jednokierunkowa. Nie deklarujemy przyspieszenia domyślnego skanu we wszystkich sytuacjach.

Cache na dysku: 1300 wpisów / 5,367,621 bajtów dla pierwszego korpusu; 52 wpisy / 3,534,031 bajtów dla drugiego. Wynik jednakowy dla oddzielnych cache Python i Rust w tych korpusach. Jest to rozmiar logiczny plików, bez narzutu bloków systemu plików. Drzewa, symbole i wywołania mogą zajmować więcej miejsca niż sam tekst źródłowy.

Kontrakt cache

Dla ustalonego silnika wynik parsera zależy od bajtów źródła, języka i jego tożsamości. Cache przechowuje ten etap, a nie gotowy graf całego projektu.

N = SHA256(tożsamość silnika, kodu parsera/modelu i zależności)
K = SHA256(język || NUL || SHA256(bajty źródła))
cache[N, K] = udany, nierozwiązany wynik parsowania
graf = resolve(bieżące ścieżki, wyniki parsowania, korzenie importów)

SHA256(bajty źródła) w kluczu jest tekstem szesnastkowym, a tożsamość jest jednoznacznie kodowana zgodnie z implementacją danego silnika. Python i Rust mają oddzielne przestrzenie. Hash zapewnia praktyczne adresowanie treści; nie jest matematycznym dowodem braku kolizji ani podpisem autentyczności cache.

Python uwzględnia wersję interpretera i pakietów oraz kod cache.py, model.py, python_parser.py, tree_parser.py. Rust uwzględnia wersję wydania, Cargo.lock oraz wbudowane bajty modułów parsera, modelu i cache. Zakładamy stabilną instalację w czasie procesu. Ręczna zmiana gramatyki bez zmiany wersji jej pakietu wymaga usunięcia cache.

Każdy wpis ma nagłówek z wersją formatu, przestrzenią, językiem, hashem źródła i hashem surowych danych JSON. Walidacja sprawdza też strukturę, typy, postać fingerprintów i brak starych rozwiązań importów/wywołań. Dane są zastosowane dopiero po walidacji całego wpisu. Nie zapisujemy błędów parsowania.

Źródła nadal są czytane w całości. Cache nie usuwa kosztu O(B) odczytu i haszowania B bajtów ani kosztu rozwiązania grafu i serializacji raportu. Pomija parsowanie trafionych plików w zamian za odczyt, walidację i deserializację wpisów. Zysk zależy od tych kosztów i od liczby trafień.

  • Nowe katalogi i pliki cache mają prywatne uprawnienia na Unix. Zapis do unikalnego pliku tymczasowego kończy się atomowym zastąpieniem wpisu. Nie ma gwarancji trwałości po zaniku zasilania: cache jest odtwarzalny, nie pełni roli bazy danych.
  • Nie śledzimy symlinków wpisów cache; cache powinien należeć do użytkownika. Suma kontrolna wykrywa uszkodzenie, ale nie przeciwnika mogącego zmienić zarazem dane i sumę.
  • Limit pojedynczego wpisu: 64 MiB. Brak limitu całego cache, automatycznego sprzątania i TTL. Katalog można usunąć po zakończeniu analiz.
  • Cache wewnątrz projektu jest jawnie wyłączony ze skanu, również z --all. Wskazanie jako cache korzenia projektu lub jego przodka jest odrzucane.
  • runtime.cache zawiera trafienia, chybienia, zapisy, uszkodzenia, błędy i zbyt duże wpisy. Przy równoczesnym zapełnianiu liczniki mogą zależeć od kolejności wykonania; wynik analizy pozostaje uporządkowany.

Sprawdzenie poprawności

43 + 2 testy zakończone powodzeniem. Nowe przypadki obejmują zmianę treści przy zachowaniu rozmiaru i mtime, aktualny bit wykonywalności, przeniesienie pliku z importem względnym, nowe moduły, zmianę --source-root, uszkodzone nagłówki i dane, niewłaściwe typy, niezgodny język, limit parsowania, Unicode w liczeniu linii, symlinki i niedostępny cache. Rust dodatkowo sprawdzono przy dwóch procesach po cztery workery, współdzielących jeden cache.

Benchmark porównuje pełne JSON-y 0.2 i 0.3, po usunięciu wyłącznie runtime: scan/diff na korpusie funkcjonalnym oraz wszystkie dziesięć wariantów obu korpusów pomiarowych. Porównanie jest wykonywane w obrębie tego samego silnika. Wszystkie warunki równości przeszły.

Nie utożsamiamy AST CPythona z CST Tree-sitter. Dotychczasowe różnice między silnikami, m.in. obsługa nawiasów i zapisu literałów Python, pozostają. Większa szybkość nie dowodzi pełnej analizy semantycznej. Zależności wywołań są statycznymi kandydatami; nie ma kompletnego CFG/PDG, inferencji typów ani dowodu równoważności programów.

Uruchomienie i LLM

# Rust: ponowne porównania tych samych lub podobnych projektów
chmod +x bin/grapholog-rs-linux-x86_64
./bin/grapholog-rs-linux-x86_64 diff ./A ./B --cache-dir /tmp/grapholog-cache --jobs 4

# Python: ten sam interfejs cache, jeden worker
grapholog diff ./A ./B --cache-dir /tmp/grapholog-cache

# Raport z Rust → pakiet dowodów dla LLM
./bin/grapholog-rs-linux-x86_64 diff ./A ./B --cache-dir /tmp/grapholog-cache --jobs 4 --format json > /tmp/diff.json
grapholog-llm prepare /tmp/diff.json --max-chars 40000 > /tmp/llm-packet.json
grapholog-llm validate /tmp/llm-packet.json /tmp/reply.json

Pakiet LLM zachowuje dobór dowodów, limit znaków oraz rozdzielenie faktów i hipotez z 0.2. Metadane cache nie są dowodami opisującymi logikę kodu. Pełny hash raportu może się zmienić wraz ze statystykami, podczas gdy odciski plików pozostają te same. Walidator sprawdza format i referencje, nie prawdziwość twierdzeń modelu. Nie wykonano żadnego wywołania API LLM.

W paczce: źródła obu silników, Python wheel 0.3.0, uruchamialne archiwum grapholog.pyz, natywna binarka Linux x86_64 wymagająca glibc co najmniej 2.34, przykłady, testy i surowe wyniki. Dodatkowe parsery Python instaluje opcja .[parsers]; nie są wbudowane w wheel ani pyz. Kod Rust jako wejście .rs nadal ma tylko inwentaryzację i SHA-256.

Wniosek: Rust pozostaje praktycznym silnikiem CLI w tym projekcie. Cache ma największy sens przy powtórnych analizach i droższych parserach. Wybór 2–4 workerów warto potwierdzić na własnym repozytorium, obserwując pamięć i dysk. Python pozostaje przydatny dla CPython AST, prototypowania i obsługi pakietów LLM.

Następne uzasadnione kroki to ograniczenie rozmiaru cache, testy na rzeczywistych repozytoriach oraz obsługa składni Rust jako wejścia. Merkle DAG, watch, MinHash/LSH, edycje AST i rozproszony harmonogram pozostają poza 0.3.
